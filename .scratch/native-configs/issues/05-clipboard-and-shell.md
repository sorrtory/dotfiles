# 05 — Yazi: three copy operations and a real shell

Status: claimed
Blocked by: 03

## Goal

Separate the operations Yazi's `;` and `:` conflate. "Copy" in a file manager
means at least three different things, and the legacy setup had a key for only
one of them; `;` and `:` are command-input boxes rather than a shell, which is
why reaching for a shell there feels wrong.

| Key | Operation |
| --- | --- |
| `y` | the **file**, onto the system clipboard as `text/uri-list` |
| `<C-p>` | the reverse: files on the system clipboard, into this directory |
| `<C-y>` | the file's **contents**, as text |
| `<A-Y>` | the same, each file behind its path in a code fence |
| `!` | a real `$SHELL` in the hovered directory |
| `c c` / `c f` | the **path** or filename as text — already a Yazi preset |

## Work

1. `configs/yazi/keymap.toml`: the five bindings above, prepended.
2. `modules/programs/yazi.nix`: add `pkgs.yaziPlugins.clipboard` to
   `programs.yazi.plugins`.
3. `packages/yazi-copy-file-contents.nix`: bump to the revision that takes a
   `plain` or `multi` argument, and regenerate `configs/yazi/package.toml`
   with `ya pkg add` rather than editing it by hand.
4. `modules/packages.nix`: add `xclip`.
5. Documentation rows for both plugins and for the X clipboard tools.

## Constraints

- **`y` must keep doing its own job.** The clipboard plugin copies whatever is
  in Yazi's yank register, so the binding runs `yank` first and the plugin
  second. Yazi's own `p` must still paste.
- None of the five keys may shadow a preset. Checked against the 26.5.6 preset
  embedded in the binary: `y` and `p` are presets and are preserved; `!`,
  `<C-y>`, `<A-Y>` and `<C-p>` are unbound there.
- `Alt+y` is retired rather than kept as an alias. That is a deliberate change
  to the behavior baseline in `spec.md`, which is amended to say so.
- Nixpkgs is the record for `clipboard.yazi`, which it carries and keeps
  current. Do not add it to `package.toml` as well; two records of one
  revision drift apart.
- The copy-file-contents bump is what buys `plain` and `multi`. The pin in
  `package.toml` moves with it, regenerated by the tool that owns that file.
- `clipboard.yazi` chooses its tool by `XDG_SESSION_TYPE`: `wl-copy` on
  Wayland, `xclip` on X11. Without `xclip` an X session — which the staging VM
  is — gets a "Copy failed" toast instead of a clipboard.

## Acceptance

- `nix build .#homeConfigurations.z.activationPackage` succeeds.
- Yazi starts with the keymap accepted; a rejected keymap falls back to preset
  settings and says so on screen.
- Each key does its own operation, confirmed by pressing it rather than by
  reading the configuration.

## Comments

Implemented on the host, and verified by pressing the keys.

The check ran Yazi inside a tmux server on a private socket, with `HOME` and
every `XDG_*` in a throwaway sandbox, the repository's `keymap.toml` symlinked
in as activation would link it, the plugin directories taken from the built
`home-manager-files`, and `wl-copy`/`wl-paste` replaced by stubs that record
what they are handed. Nothing touched the operator's clipboard, and keys were
sent into Yazi's own pty, so these are real key presses rather than commands
run behind its back.

- Yazi started with no error banner, which is what says the keymap parsed —
  including `for = "unix"` and the `<A-Y>` notation.
- `<C-y>` on a hovered file: `wl-copy` received exactly `hello from the
  sandbox`, and the plugin's notification appeared, which is the proof it
  loaded.
- `<A-Y>` with two files selected: `wl-copy` received each file behind its
  relative path, fenced with ``` and separated by a blank line.
- `y` with two files selected: `wl-copy -t text/uri-list` received
  `file:///…/hello.txt` and `file:///…/second.txt`. That is the form a GUI
  application reads as a file rather than as text.
- `<C-p>` with a `text/uri-list` on the stub clipboard: `wl-paste -t
  text/uri-list` was called and the named file appeared in the current
  directory with its content intact, with a "Pasted 1 file(s)" notification.
- `y` then `p` in another directory still copies the file the Yazi way, so
  overriding `y` did not cost the internal yank register.
- `!`: `$SHELL` opened in the hovered directory — a file written from it
  recorded `shell:/bin/bash` and the directory Yazi was showing — and `exit`
  returned to the same Yazi session.

Not verified here, and it needs a real session rather than a VM: that a paste
into Nautilus or Telegram is treated as an attachment. The stub proves Yazi
hands over the right MIME type and payload; only a GUI application can prove
it reads them.

The operator's legacy Snap Yazi is still running on the host
(`/snap/yazi/939/yazi`), so `snap list yazi` in ticket 03's acceptance remains
theirs to retire.
