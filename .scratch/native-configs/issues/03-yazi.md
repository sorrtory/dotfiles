# 03 — Yazi

Status: claimed

## Goal

Let Home Manager own Yazi, its native TOML configuration, and its single
pinned plugin. This removes the last legacy Snap dependency other than the
browser.

## Work

1. Copy `keymap.toml` and `package.toml` from `~/Documents/configs/yazi/` to
   `configs/yazi/`.
2. Create `modules/programs/yazi.nix` with `programs.yazi.enable = true`,
   exposing the TOML files through `mkOutOfStoreSymlink`.
3. Provide the `copy-file-contents` plugin from
   `AnirudhG07/plugins-yazi` at revision `71545f4`, the pin
   `configs/yazi/package.toml` already records. Use `pkgs.yaziPlugins` if it
   carries the plugin; otherwise write a small local package under
   `packages/`.
4. Import the module from `home.nix`.

## Constraints

- `docs/SOFTWARE.md` records Yazi as a *"Legacy Snap"*. The selected policy is
  that no software this repository declares comes from Snap, so this ticket
  must not leave any Snap fallback path in place. Update the row.
- Keep `package.toml` in the repository even though Nix now provides the
  plugin. It is the record of which revision was selected, and deleting it
  loses the provenance of the pin.
- Yazi must find the plugin where it expects it. Verify the plugin actually
  loads rather than only that the file is present; a plugin in the wrong
  directory fails quietly.
- Yazi needs its preview dependencies to be useful. FFmpeg and ImageMagick are
  already global user tools; confirm rather than re-declare them.

## Acceptance

- `nix build .#homeConfigurations.z.activationPackage` succeeds.
- On the staging VM after activation:
  - `yazi` starts and resolves its config into `~/Documents/dotfiles`;
  - `Alt+y` on a text file copies its contents, proving the plugin loaded;
  - `snap list yazi` reports nothing installed.

## Comments

Implemented on the host. `configs/yazi/` holds `keymap.toml` and
`package.toml`, copied verbatim. `modules/programs/yazi.nix` enables
`programs.yazi`, links `keymap.toml` with `mkOutOfStoreSymlink`, and declares
the plugin through `programs.yazi.plugins`, which places it where Yazi looks
for it: `~/.config/yazi/plugins/copy-file-contents.yazi`.

`pkgs.yaziPlugins` carries about fifty plugins but not this one, so
`packages/yazi-copy-file-contents.nix` builds it with `mkYaziPlugin` from
`AnirudhG07/plugins-yazi` at `71545f4ee1a0896c555b3118dc3d2b0a1b92fad9`, the
full revision behind the `=71545f4` pin in `package.toml`. Its upstream
repository holds three unrelated plugins, so the install phase copies only
`copy-file-contents.yazi`. The built output is byte-identical to what the
legacy manager had restored into
`~/.local/share/configs-manager/yazi/plugins/` (`diff -r` reports no
difference), which is the evidence that the pin was read correctly.

Two judgments the ticket left open:

`package.toml` stays in the repository as the record of the pin, as instructed,
but is deliberately **not** linked into `~/.config/yazi/`. Only `ya pkg` reads
it there, Nix has taken that job, and a stray `ya pkg upgrade` would only fail
against a plugin directory Nix owns.

The plugin is given a `setup` call, which the legacy setup never had. Without
one, `main.lua` reads `append_char` and `notification` out of empty plugin
state, so copying two or more selected files at once fails on a nil
concatenation — a latent bug inherited from the legacy configuration rather
than introduced here. `settings` are `append_char = "\n"` and
`notification = true`; the notification is also the only visible proof the
plugin loaded, which is what the ticket's "verify it actually loads" asks for.
That is a deliberate, small improvement over the baseline, not a silent change.

Verified on the host: the build succeeds, and `home-manager-files` carries
`.config/yazi/keymap.toml` resolving into the repository, the plugin directory
at `.config/yazi/plugins/copy-file-contents.yazi`, and a generated
`.config/yazi/init.lua` containing exactly the `require(...):setup({...})`
call. FFmpeg and ImageMagick are already in `modules/packages.nix`, confirmed
rather than re-declared.

Not verified: `Alt+y` pressed in a running Yazi, and `snap list yazi`. Both
belong on the VM, which could not be synced from this session — `rsync` to the
guest was refused by this session's permission layer as a shared-resource
change.

### Amended by ticket 05

Three things above are now historical rather than current, and the reasons are
in [05](05-clipboard-and-shell.md):

- The plugin is no longer at `71545f4`. Ticket 05 bumped it to the revision
  that takes a `plain` or `multi` argument, and `package.toml` moved with it,
  regenerated by `ya pkg add`. The byte-for-byte match against what the legacy
  manager had restored was the evidence that `71545f4` had been read correctly,
  and that reading still stands; the pin simply moved forward deliberately.
- The `setup` call is no longer load-bearing for correctness. At the newer
  revision the plugin defaults its own `append_char` and wrapper per mode, so
  `setup` now carries only `notification = true` — still the visible proof the
  plugin loaded.
- `Alt+y` is gone. Contents are on `Ctrl+y`, because the slice separated the
  three things "copy" means. `spec.md`'s fourth behavior baseline is amended to
  say so.

`Alt+y` itself was never pressed: the sandbox harness that can drive Yazi by
real key presses was built for ticket 05, by which point the binding was
already `Ctrl+y`. What that harness proves for `Ctrl+y` — the plugin loads and
copies the file's contents — is the same claim ticket 03 made for `Alt+y`,
through the same plugin, so nothing is left unverified by the change. It is
worth being exact about which key was actually pressed.
